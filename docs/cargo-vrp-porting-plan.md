# Перенос ядра DARP на грузовой VRP

Язык: **RU** | [EN](#english-summary)

Пассажирский DARP — частный случай PDPTW: каждая заявка — пара «подача → высадка»
на одной машине, с окнами и ограничением времени в пути. Грузовая задача
(доставка, сбор, перевозка «склад — клиент» на смешанном парке) отличается
единицами ёмкости, стоимостью и правилами для водителя, а не алгеброй
расписания. Ниже — что переносится без изменений, что меняется и как это
проверить.

## Что переносится как есть

| Понятие в ядре | Код | Грузовой смысл |
| --- | --- | --- |
| Пара подача/высадка на одной машине | `PICKUP_BEFORE_DROPOFF`, `PAIRING_SAME_VEHICLE`; точная модель — метки маршрутов (`solve_exact_cpsat`, `_build_mip`) | забор и доставка груза одним рейсом |
| Окна на обоих концах | `pickup_service_floor`, нотариус `check_route` | слоты погрузки на складе и разгрузки у клиента |
| Ужатие окон (Dumas–Desrosiers–Soumis 1991) | `domain/constraints.py` | то же правило для слотов «приехать не раньше» |
| Гетерогенный парк | `Vehicle`: `passenger_capacity`, `wheelchair_capacity`, `lift_available`, `compatible_wheelchair_types`, `service_area`, смены | грузоподъёмность и вторая размерность (паллеты), гидроборт, тип кузова, зоны въезда |
| Совместимость «заказ — машина — водитель» | `accessibility_compatible`, `DriverIndex`, `DRIVER_QUAL` | допуск ДОПОГ, категория прав, обучение на технику |
| Перерывы и недоступность | `unavailable_intervals`, `DRIVER_REST` | режим труда и отдыха водителя, ТО |
| Вставка с префиксным состоянием (Rust) | `native/mobiroute_native` | та же операция для доставок |
| Независимая проверка + сертификат «почему нельзя» | `verify_routes`, `ScheduleCertificate` | объяснение логисту, какой слот или лимит ломает рейс и на сколько минут |
| Онлайн-вставка, отмена, поломка, повторное планирование | `dispatch/online_insertion.py` | срочный заказ, отказ клиента, выход машины из строя |

## Что меняется

1. **Многомерная ёмкость.** Сейчас две размерности (места и колясочные места).
   Обобщить до вектора `capacity: dict[str, int]` (кг, м³, паллеты) в модели,
   Rust-таблице заявки (stride 16 → переменный хвост) и нотариусе.
2. **Стоимость по типу машины.** Целевая функция ядра — длительность маршрутов;
   для груза нужна стоимость: постоянная за выход машины + переменная за км и час
   по типу ТС. В точной модели это коэффициенты при дугах для каждого типа.
3. **Гетерогенный парк в точной модели.** Метки маршрутов уже держат заявку на
   одной машине; добавляется переменная типа ТС для маршрута (элемент-ограничение
   на ёмкость и стоимость) и лимит числа машин каждого типа.
4. **Время в пути груза.** Ограничение `max_ride_time` становится необязательным
   (скоропортящийся груз — да, обычный — нет), а ограничение длительности смены
   водителя — главным.
5. **Данные.** Матрица времени по дорожному графу с учётом ограничений для
   грузового транспорта (зоны въезда, мосты, высота). Ядро уже принимает
   произвольную матрицу и считает кратчайшие пути (Флойд–Уоршелл).

## Этапы и критерии приёмки

| Этап | Результат | Как проверяется |
| --- | --- | --- |
| 1. Литературная проверка | загрузчик Li & Lim (2001) PDPTW и Solomon (1987) VRPTW в точную дорожку | на малых инстансах оптимум CP-SAT/MIP совпадает с опубликованным; нотариус независим |
| 2. Многомерная ёмкость | `capacity` как вектор в модели, Rust и нотариусе | паритет Python-оракула и Rust на случайных маршрутах; красная команда на перегруз |
| 3. Стоимость и типы ТС | целевая функция «выход + км + час», лимиты по типам | точная модель на синтетическом парке из 2–3 типов; эвристики не хуже точного решения больше заданного разрыва |
| 4. Эвристики на масштабе | ALNS с regret-вставкой и ограничением по времени | разрыв к лучшим известным решениям Li & Lim, публикуется только после верификации |
| 5. Пилот на данных клиента | обезличенный выгрузочный день | сравнение с текущим планом по пробегу, числу машин, опозданиям; сертификаты для каждого отказа |

## Чего здесь нет

Нет данных клиента, нет обещаний по экономии. Цифры появляются только после
этапа 5 и проходят тот же контур: независимая проверка, запрет на неподтверждённый
разрыв к литературе.

## English summary

Passenger DARP is a PDPTW with ride-time limits. Porting it to cargo routing
keeps the scheduling algebra (paired pickup/delivery, two-sided windows, valid
window tightening, driver rest, Rust prefix-state insertion, independent
notary with negative-cycle certificates, online re-planning) and changes the
units: a capacity vector (kg, m³, pallets), per-vehicle-type fixed and variable
costs, a vehicle-type variable per route in the exact model, an optional
cargo ride limit, and a truck-aware travel matrix. Stages: Li & Lim / Solomon
loaders verified against published optima on small instances; capacity vector
with Python/Rust parity; cost and fleet-mix model; time-boxed ALNS with gaps
published only after verification; a pilot day on anonymised client data.
