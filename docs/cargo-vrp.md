# Грузовой VRP со смешанным парком

Язык: **RU** | [EN](#english-summary)

Пакет `mobiroute.vrp` решает задачу маршрутизации, в которой у каждого заказа
есть окна, вес, объём и паллеты, требования к кузову и к допуску, а у парка —
несколько типов машин, свои и наёмные, с разной стоимостью, скоростью и
длительностью смены. Это тот же класс задач, что пассажирский DARP, но с
грузовыми единицами и экономикой парка; пассажирские сценарии (шаттл по
требованию) решаются той же моделью.

## Модель

| Понятие | Как задаётся | Пример |
| --- | --- | --- |
| Заказ «забор → доставка» | `Request(pickup, delivery)` | поставщик → клиент |
| Доставка со склада | `Request(None, delivery)`, груз на борту с начала рейса | РЦ → магазин (VRPTW) |
| Сбор на склад | `Request(pickup, None)` | возврат тары |
| Вектор ёмкости | `demand`, `capacity` любой размерности | кг, м³, паллеты |
| Требования к машине | `skills` заказа ⊆ `skills` типа | гидроборт, рефрижератор, ДОПОГ, кран |
| Типы машин | `VehicleType`: количество, депо, смена, профиль скорости | фургон 1,5 т, 5 т, 10 т, тягач 20 т |
| Свои и наёмные | свои: только переменные затраты; наёмные: плата за выход + тариф выше | решение нанимает, только когда своих не хватает |
| Стоимость | `fixed_cost + руб/км × км + руб/ч × (движение + обслуживание)` | |
| Окна | начало обслуживания в `[earliest, latest]` | слот разгрузки у клиента |
| Смена водителя | `max_duration`: от выезда до возврата | 10 часов |
| Режим труда и отдыха | `BreakRule(max_driving, duration)` | 4,5 ч за рулём → перерыв 45 мин, не больше 9 ч вождения за смену |
| Несколько рейсов | `reload_nodes`, `max_trips`: точки повторной загрузки на складе | утренняя и дневная волна одной машиной |
| Пробки по часам суток | `SpeedProfile`: доля скорости свободного потока по периодам | 55% в 07:30–10:00, 60% в 17:00–19:30 |
| Время в пути груза | `max_ride` для пары | скоропортящийся груз |
| Профили дорог | матрицы времени и расстояния на тип | грузовик медленнее фургона |

Формально — [mathematical-formulation.md](mathematical-formulation.md), раздел 1.

## Как решается

1. **Построение.** Regret-2: на каждом шаге вставляется заказ, у которого
   разница между лучшим и вторым вариантом наибольшая — сначала те, кому
   «некуда деться».
2. **Вставка за O(1).** Для маршрута хранятся самое раннее и самое позднее
   начало обслуживания на каждой остановке и загрузка по каждому измерению.
   Проверка окна, ёмкости и навыков — арифметика; кратчайшая длительность рейса
   после вставки — по готовой формуле из префиксных и суффиксных экстремумов.
   Лимит времени в пути проверяется точно (Беллман–Форд) только для самых
   дешёвых кандидатов.
3. **ALNS.** Разрушение: случайное, худшие, связанные (Shaw), цепочки с соседних
   маршрутов (SISR), маршрут целиком; восстановление: regret-1/2/3, с шумом и
   без; веса операторов адаптируются, приём решений — имитация отжига.
4. **Меньше машин.** Убираем маленький маршрут и возвращаем его заказы методом
   guided ejection: вставка ценой выталкивания не более двух других заказов с
   наименьшими штрафами, затем возмущение.
5. **Тип машины для маршрута.** Вставка открывает машину ради одного заказа,
   поэтому тип с большой платой за выход сам по себе не выбирается никогда, даже
   если весь маршрут на нём дешевле. После каждого восстановления типы
   маршрутов выбираются заново и точно — как транспортная задача (поток
   минимальной стоимости «маршрут → тип», не больше `count` машин типа).
   Отдельный оператор сливает два маршрута в один на машине другого типа,
   когда так дешевле, и сцепляет рейсы: маршрут A + повторная загрузка + маршрут B
   (в том числе B, снятый с наёмной машины).
6. **Локальный поиск.** Для задач с доставками со склада (VRPTW) каждый новый
   лучший план проходит спуск relocate / swap / 2-opt* / 2-opt; окна
   проверяются за O(1) склейкой временных сегментов (Vidal et al. 2013).
7. **Разбиение множества (опция).** Маршруты принятых планов собираются в пул,
   модель set partitioning решается CP-SAT, SCIP, HiGHS или CBC
   ([benchmarks/setpart-solvers.md](benchmarks/setpart-solvers.md)).
8. **Цены заказов и машин.** Двойственная задача LP-релаксации той же модели
   (GLOP) даёт цену каждого заказа и ренту типа машины, которого не хватило
   (`vrp-solve --prices`). В пул добавляются маршруты плана без одного заказа,
   поэтому у плана, оптимального для LP, цена заказа не ниже экономии при
   отказе от него (лемма 5). Задача вырожденная, оптимальных двойственных
   решений много; вторым LP по оптимальной грани выбирается ближайшее к
   экономии при отказе. Это цены ограниченной мастер-задачи: точные для пула,
   оценка для задачи в целом.
9. **Необязательные заказы.** Заказ со штрафом за отказ обслуживается, только
   пока это дешевле штрафа: после восстановления из плана по одному убираются
   заказы, которые дороже возить, чем отказать, а затем целиком маршруты из
   необязательных заказов, если рейс дороже суммы штрафов. Против точной
   модели: оптимум в 87 задачах из 90 (без этого шага — в 16)
   ([benchmarks/exact-vs-alns.md](benchmarks/exact-vs-alns.md)).
10. **Ядро на Rust.** Восстановление, вставка, точная проверка расписания (с
   перерывами и рейсами) и шаг выталкивания выполняются в `VrpKernel`.
   Результат совпадает с эталоном на Python бит в бит, вплоть до всей
   траектории ALNS ([benchmarks/vrp-speed.md](benchmarks/vrp-speed.md)).
   Задачи с пробками идут на эталоне Python.

## Как проверяется

* **Независимый верификатор** пересчитывает загрузку, расписание и стоимость
  любого плана — эвристики, CP-SAT или OR-Tools — и ничего не берёт у решателя.
* **Сертификат «почему нельзя».** Если рейс невозможен, верификатор возвращает
  отрицательный цикл в графе ограничений: какие условия конфликтуют и сколько
  минут не хватает. Пример с грузового дня: *поставщик открывается в 09:00,
  погрузка 26 мин, переезд 162,8 мин, клиент принимает до 12:00 — не хватает
  8,8 мин*. Логист сразу видит, что менять: окно клиента или время у поставщика.
* **Точная модель.** CP-SAT с отдельным циклом на каждую машину доказывает
  оптимум на малых задачах: на 40 случайных задачах полной модели ALNS находит
  доказанный оптимум во всех 40 случаях
  ([benchmarks/exact-vs-alns.md](benchmarks/exact-vs-alns.md)).
* **Открытые эталоны.** Solomon, Li & Lim, Sartori–Buriol (реальные дорожные
  времена OSRM), Cordeau — разрыв к лучшим известным решениям по каждому
  инстансу ([benchmarks/vrp-public-benchmarks.md](benchmarks/vrp-public-benchmarks.md)).
* **OR-Tools.** Та же модель в OR-Tools Routing (PCI + GLS) при равном времени,
  тот же верификатор: на грузовых днях ALNS дешевле на 14–17% и обходится меньшим
  числом машин, на открытых эталонах лучше на 9 задачах из 15 и не хуже нигде
  ([benchmarks/ortools-vs-alns.md](benchmarks/ortools-vs-alns.md)). Матрицы
  OR-Tools получает на стороне C++, а не через колбэки Python: иначе его время
  уходило бы в интерпретатор.
* **PyVRP, VROOM, jsprit.** Те же задачи, то же время, один поток, тот же
  верификатор. На Solomon (сначала число машин) только этот движок держит
  число машин лучшего известного решения на всех 56 задачах (PyVRP 50, VROOM
  32, jsprit 30); на 1000 клиентов, где считается только расстояние, впереди
  PyVRP (+1,2% к лучшему известному), этот движок второй (+2,9%)
  ([benchmarks/solvers.md](benchmarks/solvers.md)).

## Сценарии

**Городская доставка со своим и наёмным парком** (`generators.cargo_day`). Два
депо, 4 класса машин, своих и наёмных, вектор кг/м³/паллеты, рефрижератор,
гидроборт, ДОПОГ, слоты доставки, смена 10 часов. На дне из 60 заказов решение
обходится своими машинами; на 120 заказах добавляет наёмные только того класса,
которого не хватает.

**Внутризаводская логистика в реальном времени** (`generators.plant_day`,
`realtime.Dispatcher`). Перевозки паллет между цехами и складами появляются в
течение смены; тягачи, бортовые машины с краном, крытый фургон. Каждая заявка
получает ответ за доли миллисекунды: вставка в ту часть плана, которую машина
ещё не проехала, или отказ с причиной. Раз в 30 минут живое состояние
переоптимизируется ALNS. Метрики: доля принятых заявок, время подачи (от
заявки до прибытия машины), стоимость. Для сравнения — пересчёт всего живого
состояния в OR-Tools на каждую заявку: на 2,8 п. п. больше принятых заявок и на
1,6% дешевле, но 2,9 с на решение вместо 0,1 мс и подача машины в среднем на
5 минут позже ([benchmarks/realtime-dispatch.md](benchmarks/realtime-dispatch.md)).

**Распределительный центр → магазины, две волны** (`generators.dc_day`). 60
магазинов, утренние слоты 07:00–10:00 и дневные 13:00–16:00, 1–4 паллеты,
свои фургоны и грузовики, наёмные — с платой за выход, режим труда и отдыха
включён. При одном рейсе на машину день не закрывается даже всеми наёмными;
при двух рейсах своих машин хватает почти на всё
([benchmarks/rules.md](benchmarks/rules.md)).

**Режим труда и отдыха и пробки на грузовых днях.** Тот же грузовой день,
спланированный без нормы 4,5 ч, проверяется верификатором уже с нормой: на
части маршрутов перерыв поставить некуда, сертификат называет минуты.
Аналогично план на скоростях свободного потока проверяется в часы пик
([benchmarks/rules.md](benchmarks/rules.md)).

**Корпоративный шаттл по требованию** (`generators.shuttle_day`). Поездки
между остановками; ожидание не больше 30 минут, ожидание плюс поездка не
больше 45 минут, микроавтобусы на 8 мест. Ограничение «ожидание + поездка»
записывается точно — как крайний срок высадки.

## Данные из координат и маршрутные листы

**Вход.** `mobiroute.vrp.geo` читает заказы и парк в координатах (JSON,
формат `mobiroute.vrp.geo.v1`, полный пример — в docstring модуля). Время —
строки «ЧЧ:ММ», длительности — минуты, расстояния — километры.

| Поле | Что задаёт |
| --- | --- |
| `depots[]` | склады: `lat`, `lon`, часы работы `open` / `close`, время погрузки перед выездом `load_min` (входит в смену и в окна) |
| `orders[].pickup`, `orders[].delivery` | точки погрузки и выгрузки: координаты, окно `from` / `to`, `service_min`, название. Без `pickup` груз берётся на складе, без `delivery` — везётся на склад |
| `orders[].demand`, `skills`, `penalty`, `max_ride_min` | груз по измерениям `dimensions`, требования к машине, штраф за отказ (без штрафа заказ обязателен), лимит времени в пути |
| `vehicle_types[]` | число машин, ёмкость, склад выезда и возврата, смена, лимит длительности, плата за выход, цена километра и часа, навыки, профиль, `hired` |
| `vehicle_types[].rests` | норма отдыха: `max_driving_min`, `duration_min` |
| `vehicle_types[].trips` | рейсы: `max` и время повторной загрузки `reload_min` |
| `profiles` | `speed_kmh` и коэффициент извилистости `detour` для офлайн-матриц; `osrm_time_factor` — замедление грузовика на матрицах OSRM |
| `traffic` | пробки: начала периодов и доли скорости свободного потока |
| `currency` | подпись к стоимости в маршрутных листах (`RUB` → ₽) |
| `zones[]` | зоны (многоугольник `polygon` или круг `center` + `radius_km`) с пределами `max_gross_weight_t`, `max_axle_load_t`, `max_height_m` и запретом типов `banned_types` — как знаки 3.11, 3.12, 3.13 и 3.4 |
| `vehicle_types[].gross_weight_t`, `axle_load_t`, `height_m` | характеристики машины, по которым зоны её пускают или нет |
| `vehicle_types[].rests.split_min` | разделённый перерыв, например `[15, 30]` |
| `profiles.*.valhalla` | грузовая стоимость Valhalla: `{"costing": "truck", "options": {"weight": 12, "height": 3.8, "axle_load": 8, "hazmat": false}}` для `--valhalla URL` |
| `time_cost` | `"duty"` — цена часа за всю смену с ожиданием; по умолчанию `"operating"` — за вождение и работу |

Ошибка входа называется кодом: `GEO_DUPLICATE_ORDER:A17`,
`GEO_COORDINATES_INVALID:A17.delivery`, `GEO_UNKNOWN_DEPOT:van`; дальше модель
проверяет себя сама (`VRP_CAPACITY_INVALID:van`). CLI печатает такую ошибку
одной строкой в stderr и завершается с кодом 2.

**Матрицы.** Офлайн: расстояние по дуге большого круга (гаверсинус),
умноженное на коэффициент извилистости, время — по средней скорости профиля.
Этого хватает, чтобы попробовать движок на реальных адресах. С сервером OSRM
(`--osrm URL`) работает сервис `table` (Luxen & Vetter 2011): длительности и
расстояния запрашиваются блоками до 100 × 100 точек (предел
`--max-table-size` по умолчанию), секунды и метры переводятся в минуты и
километры. Пара точек без маршрута — ошибка `GEO_OSRM_NO_ROUTE:i->j`, а не
молчаливый ноль.

**Расписание для водителя.** Самое раннее расписание, по которому верификатор
проверяет окна, выезжает в начале смены и может час простоять у первого
клиента. В маршрутном листе выезд назначается на момент «самое раннее
возвращение минус кратчайшая длительность», дальше — самое раннее расписание
от этого выезда (`schedule.compact_schedule`). Почему оно допустимо и
кратчайшее: проекция системы разностных ограничений на пару «выезд,
возвращение» — снова система разностных ограничений:
`L₀ ≤ t₀ ≤ U₀`, `Lₑ ≤ tₑ ≤ Uₑ`, `c ≤ tₑ − t₀ ≤ C`, где `c` — кратчайшая
длительность. Самое раннее возвращение `E = max(Lₑ, L₀ + c)`, и точка
`(E − c, E)` проекции принадлежит: `E − c ≤ U₀`, потому что путь
«возвращение → ноль часов → выезд» даёт `c ≥ Lₑ − U₀`. При пробках выезд
выбирается среди точек излома функции длительности, как в верификаторе.
Тесты на Hypothesis сверяют такое расписание с каждым ограничением на сотнях
случайных маршрутов, с перерывами, лимитами поездки и пробками.

**Маршрутный лист.** На машину: погрузка и выезд, прибытие, начало и конец работ на каждой
точке, загрузка после неё по каждому измерению и рейсу, повторная загрузка между
рейсами, перерыв водителя там, где его поставил верификатор, возвращение;
пробег, время за рулём, ожидание и стоимость (сумма по листам равна стоимости
плана). `route-sheets.csv` — строка на событие, для учётной или
диспетчерской системы; `route-sheets.md` — таблица на машину, по-русски или
по-английски (`--lang en`); `route-sheets.svg` — диаграмма Ганта всего дня:
в пути, ожидание окна, работа на точке, повторная загрузка, перерыв. В каждом
листе — проверка режима труда и отдыха (самый длинный отрезок за рулём до
перерыва, вождение за смену и длительность смены против лимитов) и порядок
загрузки кузова на складе по рейсам: обратный порядку выгрузки. Числа для
людей — с десятичной запятой, в CSV — с точкой.

Маршрутный лист — план рейса для водителя, а не путевой лист: путевой лист обязателен по ст. 6 Устава автомобильного транспорта (259-ФЗ), его реквизиты (сведения о машине и водителе, показания одометра, отметки о медосмотрах и о контроле технического состояния) установлены приказом Минтранса России № 390 от 28.09.2022 и ведутся в учётной системе; CSV маршрутных листов загружается в неё как задание.

**Пример** — синтетический день в Набережных Челнах
([examples/chelny-day.geo.json](../examples/chelny-day.geo.json)): склад, три
поставщика, 45 заказов в утренних, дневных и вечерних слотах, четыре своих
фургона с правом второго рейса, два своих грузовика, наёмные фургоны и
грузовики с платой за выход, норма отдыха у всех. Точки случайны внутри
границ города, названия помечены «условн.»: данные не описывают ни одну
компанию, их пишет [генератор](../examples/make_chelny_day.py). ALNS за 2.2 с
закрывает день семью машинами: все четыре фургона — в два рейса, из наёмных —
один грузовик.

## Запуск

```bash
mobiroute vrp-solve --generate cargo --orders 120 --out-dir out-cargo --svg
mobiroute vrp-solve --instance benchmark/instances/sartori-buriol/n100/bar-n100-1.txt --time-limit 10 --out-dir out-sb --svg
mobiroute vrp-solve --generate cargo --orders 60 --solver ortools --time-limit 10 --out-dir out-ortools
mobiroute vrp-dispatch --day plant --policy insertion+alns --out-dir out-plant
mobiroute vrp-solve --geo examples/chelny-day.geo.json --sheets --out-dir out-chelny
mobiroute vrp-solve --geo examples/chelny-day.geo.json --prices --out-dir out-prices
```

## English summary

`mobiroute.vrp` routes a heterogeneous own-and-hired fleet: capacity vectors
(kg, m³, pallets), skills (tail lift, refrigeration, ADR, crane), per-type
speed profiles, fixed and variable costs, shift caps, time windows,
pickup-and-delivery pairs, depot deliveries and collections, ride limits,
driver rests (4.5 h / 45 min), multi-trip days with reloads at the depot, and
speeds that change over the day.
Insertion tests run in constant time (forward/backward slack, a closed-form
shortest duration); ALNS with five ruin operators, regret repair and guided
ejection does the search; the repair runs in a Rust kernel that reproduces the
Python reference bit for bit. Every plan is checked by an independent verifier
that returns why-not certificates. Orders and fleet can also come as
coordinates (`mobiroute.vrp.geo`: offline great-circle matrices or the OSRM
`table` service), and a verified plan becomes route sheets (CSV, Markdown)
whose schedule leaves the depot as late as the earliest return allows, which
is a shortest feasible schedule (proof above, property-tested). Results:
public benchmarks, ALNS against CP-SAT proven optima, OR-Tools Routing at
equal time, and live dispatch on synthetic plant, shuttle and freight days —
see `docs/benchmarks/`.
